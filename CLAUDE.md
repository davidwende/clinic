This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running the Application

```bash
source ./venv/bin/activate
python -m Application_Main.main
# OR
./run_clinic.sh
```

## Architecture Overview

This is a PySide6 desktop medical records system for a musculoskeletal medicine clinic. It uses Pony ORM over SQLite (or MySQL) and follows an MVC-like pattern.

**Module layout:** Each feature area (Blood, Visits, Past_History, Reports, Patient_Data, DiagProc) is a self-contained package with a logic file and a `UI/` subdirectory containing the hand-written PySide6 UI class.

**Application flow:**
1. `Application_Login/Login.py` — SHA256-authenticated login, emits `login_success` / `login_admin` signals
2. `Application_Main/main.py` — `MainWindow` is the central hub; manages the patient list, search, and launches child form windows
3. Domain module forms connect back to `MainWindow` via Qt signals/slots

**Database layer:**
- `Database/dbCreate.py` — Pony ORM entity definitions (schema). Key entities: `PatientCore` (PK: `tz`, the 9-digit Israeli ID), `Visits` (PK: `patient` + `visit_date`), `PastHistory`, `BloodPulse`, `Procedures`, `Diagnoses`
- `Database/dbFuncs.py` — All DB operations; every function is wrapped in `@db_session`. It has an unused `from PySide6.QtCore import QDate` import, but no function body actually touches Qt — the DB layer (including `validate_tz`, patient CRUD, email/phone checks) is genuinely portable to a non-Qt context.
- Connection type (sqlite/mysql) and database creation flag are controlled by `Config/config.toml`. **Currently set to `mysql`** pointing at a Tailscale IP (not local sqlite) — multiple desktop-app installs already share one central DB over the network today.
- `Database/dbCreate.py` supports a `CLINIC_DB_TYPE` env var that overrides `config.toml`'s connection type (e.g. `CLINIC_DB_TYPE=sqlite`). Added so `html_server` (and ad-hoc testing) can target local sqlite without touching the checked-in mysql config; unset, behavior is unchanged.

**Configuration:** `Config/config.toml` holds hashed user credentials, DB connection settings, report save path, printer type, and bilingual (Hebrew/English) HTML report header/footer templates.

## Key Patterns

- **Israeli TZ validation** — Luhn-like algorithm used in multiple places; canonical implementation is in `Database/dbFuncs.py`
- **Patient search** — `QSortFilterProxyModel` with a 200 ms debounce timer in `Application_Main/main.py`
- **Reports** — Generated as HTML with embedded signature/stamp images; output to file or physical printer based on config
- **Custom widgets** — `HoverButton` and `HoverButtonVisit` live in `my_classes.py` and are used across the UI
- **Error codes** — Centralised in `error_codes.py`; `match/case` is used in save handlers
- **Visits dual-model pattern** — `Visits/visits.py` maintains two parallel list models for procedures and diagnoses: `lv_model_proc` / `lv_model_diag` (current visit display) and `lv_model_proc_list` / `lv_model_diag_list` (library picker populated once at init). The backing dicts `visit_procs` and `visit_diags` are what actually get written to the DB on save. These dicts must always be reset together with their display models in `clear_visit_form`; clearing only the model entries while leaving the dicts populated causes stale data to be saved to new visits.
- **Reports content vs. rendering are decoupled** — `Reports/reports.py` builds the report as a plain HTML string (`Report` class), then hands it to `QPrinter`/`QPrintDialog` for output. Only the output step is Qt-bound; the HTML-generation logic has no Qt dependency.

## Known Issues / Traps

- **`Patient_Data/PatientDataForm.py` + `Patient_Data/UI/patient_data_window.py` is dead code.** It's never imported by the running app. It's an incomplete stub (7 widgets, no email/phone/smoking/consent, Save button just does `print("Save pressed")`) — do not confuse it with the real patient CRUD UI, which is embedded directly in `Application_Main/main.py`'s `MainWindow` (patient list, search, the 9-field detail panel, save/modify/delete/clear, and the separate "Modify TZ" flow).
- **Secrets are checked into git.** `Config/config.toml` holds the live MySQL password reference and all users' SHA256 credential hashes; `Database/dbCreate.py` (around the mysql `db.bind(...)` call) has a hardcoded plaintext DB password in source. Auth itself is unsalted SHA256 against 3 hardcoded users in `config.toml`, with admin status keyed off a literal username check (`if username == "david"`) — not a real role system.
- **`BloodPulse.pulse/systolic/diastolic` are now `Optional(int, size=8, unsigned=True)`** (`Database/dbCreate.py`) — none of the three are ever negative, and `check_blood` (`Blood/blood.py`) validates systolic up to 254, which a *signed* 8-bit int can't hold (max 127). Unsigned size=8 covers 0-255. This was a real bug at three levels, not just a MySQL storage-width risk: Pony's own Python-level bounds check (independent of any DB backend) already rejected any systolic/pulse reading above 127 with a raw `ValueError`, which is what `html_server`'s Blood tab hit immediately. Fixed at the entity level, and `html_server/app/blood/routes.py`'s `_validate_reading` now also rejects negative values before they'd otherwise hit that same Pony bounds check as an unhandled 500. **Caveat:** `config.toml`'s mysql connection runs with `create="no"`, and Pony's `check_tables=True` only verifies columns exist by name, not their type — so this change does *not* retroactively widen the live production MySQL columns. Widening those needs a manual `ALTER TABLE bloodpulse MODIFY pulse TINYINT UNSIGNED, MODIFY systolic TINYINT UNSIGNED, MODIFY diastolic TINYINT UNSIGNED;` (or equivalent), run by hand against production when convenient — not run as part of this change.
- **Pony's SQLite time-column reads are inconsistently typed.** `BloodPulse.time` (a Pony `time` column) comes back as a real `datetime.time` for a row still in Pony's identity map (just inserted, same `db_session`) but as a plain `str` for rows freshly loaded from a committed SELECT. `get_all_blood`'s sort (`Database/dbFuncs.py`) now sorts on `str(a[0])` to normalize this; `delete_blood_from_db` uses a query-based `select(...).delete(bulk=True)` rather than `BloodPulse[v, time].delete()`, since the object-lookup path round-trips through the same inconsistently-typed cached attribute and raised `AttributeError: 'str' object has no attribute 'isoformat'`. Worth keeping in mind for any other code that reads a `BloodPulse.time` back and writes it somewhere (a primary key, a sort, a comparison) — this class of bug wasn't visible in the Qt app because `Blood/blood.py` never re-queries readings in the same session as an insert (it optimistically appends to the on-screen table instead).
- **`Reports/reports.py`'s `Report.create_string()` had several copy-paste bugs, now fixed:** a `self.h2("Ankle")` inside the hip block (should say `"Hip"`); Knee `MCL`/`LCL` left/right lines all reading `knee_lcl_r`/`knee_lcl_lax_r` regardless of which one they were labeled; a knee "Scarring (right)" line reading the `_l` fields; `"Suppinated"` misspelled; and two `interesting([...])` visibility-gate lists for `hip_passive`/`hip_resisted` that referenced the wrong field (a vestigial always-`False` boolean instead of `hip_passive_flexion_r_le`, and a leaked passive-motion field instead of `hip_resisted_adduction_r`) — those two only ever affected whether a subheading appeared, not which patient data showed under which label.

## html_server (browser-based frontend, in progress)

FastAPI service in `html_server/` that reuses the existing `Database` package (same Pony schema, same DB the desktop app points at) behind a browser UI. Implements patients, past-history, visits (+ summary/report), blood/pulse, and diag/proc — equivalents of `MainWindow`'s patient panel, `PastHistoryForm`, `VisitForm`, `BloodForm`, and `DiagProcWindow`. Every desktop module now has a web equivalent.

- **Run from the repo root** (not from `html_server/`) — `Config/config.py` and `Database/dbCreate.py` both open paths relative to cwd:
  ```bash
  cd /home/dwende/repo/clinic
  PYTHONPATH=html_server venv/bin/uvicorn app.main:app --reload
  ```
- **Structure:** `app/main.py` (FastAPI app + session middleware), `app/db.py` (imports `Database.dbCreate` to bind Pony), `app/security.py` + `app/user_store.py` (bcrypt-hashed accounts in gitignored `data/users.json`, replacing the desktop app's SHA256/hardcoded-username scheme), `app/deps.py` (login-required dependencies for page vs. API routes), `app/schemas.py` (Pydantic models), `app/validation.py` (reuses `Database.dbFuncs.validate_tz`; reimplements the phone-format rule since the original `check_good_phone` lives in a PySide6-importing file), `app/auth/routes.py` (`/login`, `/logout`), `app/patients/routes.py`, `app/past_history/routes.py`, `app/visits/routes.py`, `app/blood/routes.py`.
- **Patients** (`/patients` page + `/api/patients`): matches `save_new_patient`/`modify_patient`/`delete_patient`/`modify_patient_tz` semantics including the "invalid TZ, save anyway?" confirm flow via `?force_tz=true`. The selected patient's tz is mirrored into `sessionStorage` (`clinic_selected_tz`) on every selection/modify/TZ-change, and restored on page load if that patient is still in the (possibly filtered) list — this is what makes the "ongoing patient" stay selected after a round trip to Visits/Blood/Past History and back, regardless of how you get back there (the explicit link, browser back button, etc.), since it doesn't depend on the URL. Cleared on Clear/Delete, and silently dropped on load if the stored tz no longer resolves (deleted, or filtered out by a leftover search term) rather than showing an error.
- **Past history** (`/patients/{tz}/history`): bundles core fields + NAC/AC medication lists in one GET/PUT, plus `/api/nacs` and `/api/acs` for cross-patient autocomplete. Save semantics differ slightly from the Qt form on purpose: `PastHistoryForm` only calls `save_nacs`/`save_acs` when its `nacs_changed`/`acs_changed` flags are set; the web PUT always overwrites both lists with whatever the client sends. Same end result, simpler — no client-side dirty tracking needed.
- **Visits** (`/patients/{tz}/visits`, the ~250-field exam form): `app/visits/field_lists.py` is the single source of truth for the 9 field-order lists (`cc`/`loc`/`back`/`hip`/`neck`/`shoulder`/`knee`/`ankle`/`anklest`) that `Database.dbFuncs.save_visit` expects as positional tuples — both the generated `VisitIn`/`VisitOut` Pydantic schema (via `pydantic.create_model`) and the route's tuple-building code read from it, so there's exactly one place the field order has to be right. The lists were transcribed from `dbFuncs.save_visit`'s own `v.<field> = <group>[i]` assignments, not from the Qt UI's construction order (which has a couple of unrelated *display*-only bugs, e.g. `back_trend_l`/`back_trend_l_pos` getting swapped when repopulating the form — not replicated here). Verified with a full 257-field round-trip (alternating true/false + unique string markers, zero mismatches) before relying on it. Field labels in `static/js/visit_fields.js` are the real clinical terms (SLR, FABERE, Trendelenberg, Jobe's, McMurray's, etc.), transcribed from `Visits/UI/uiVisitsForm.py`'s widget constructors — that file is hand-written Qt code (not `.ui`-compiled), so labels are literal string arguments, not `retranslateUi()` text. `hip_resisted_flexion_l/r`, `hip_resisted_extension_l/r`, and the boolean variants of `hip_passive_med_rot_*`/`hip_passive_flexion_*` are real columns on `Visits` but are never read or written by `save_visit` or the Qt UI — deliberately left out of the web form too, to stay an exact equivalent of what the desktop app actually does.
  - The exam form is one continuous scrollable page, not a hide/show tab widget — the top nav bar (sticky, with a Save button embedded in it) scrolls to sections via `scrollIntoView` rather than toggling visibility. Every section has a heading (`<h3>`) including the three big single-textarea tabs (Examination/Tests/Recommendations), which is also why the CSS `scroll-margin-top` on `.tab-pane` needs to stay ≥ the sticky bar's actual rendered height.
  - Save/Delete are today-only (Save has no override even for admins, matching the Qt rule exactly; Delete allows admin to act on any past date, matching `Visits/visits.py`'s `admin_mode` check).
  - Summary tab (`GET /api/patients/{tz}/visits/{date}/report`) reuses `Reports.reports.Report` as-is for the HTML content; "Print / Save as PDF" opens the report in a new tab and calls `window.print()` there (letting the browser's native print-to-PDF handle it — no server-side PDF renderer); "Download as HTML" saves the same content as `{tz}_{date}.html` client-side. No today-only restriction on viewing a summary, matching the Qt app.
  - The report's two images (clinic logo, signature stamp) come from `Config/config.toml`'s `header`/`tail` strings as hardcoded `file:///home/dwende/repo/clinic/...` URLs — that works in the Qt app's native renderer but a real browser refuses to load `file://` from an http(s) page. Rather than edit `config.toml` (shared with the desktop app, which would break its own rendering), `get_visit_report` rewrites just its own copy of the HTML, swapping those two `file://` URLs for `/report-assets/{filename}` — a new route in `app/visits/routes.py` that serves only `logo_small.png`/`signature_stamp.png` from `REPO_ROOT` (`app/config.py`) via an exact-match allowlist (`REPORT_IMAGES`), not a directory mount, so it can't be used to read arbitrary repo files (confirmed: `/report-assets/config.toml` and a `..`-encoded traversal both 404).
  - `get_visit_report` also rewrites the report's `<title>` (regex, since `config.toml`'s original `<title > Patient Summary </title>` has irregular whitespace) to `_report_filename_stem(tz, visit_date)` -- `"{tz}_{YYYYMMDD}"`, e.g. `123456789_20260820`. This is the only lever available for the "Print / Save as PDF" filename: browsers derive the suggested Save-As-PDF filename from the document title, there's no other API for it. Deliberately not the same convention as `Visits/visits.py`'s own `print_summary()` (`f"{tz}_{visit_date}.html"`, which includes dashes via `str(date)`) -- a compact-date filename was requested separately for the web app specifically. "Download as HTML" matches it client-side by stripping dashes from `currentDate` rather than calling the same Python helper, since that path never goes through the server's title rewrite.
  - **Unsaved-changes leave guard** (`static/js/visits.js`): the Qt `VisitForm` has no equivalent of this -- it's a browser-only safeguard added because a tab/page navigation loses in-progress edits silently, which a desktop dialog never would. Dirty tracking is a JSON-snapshot diff (`baselineSnapshot`, captured on every load/save via `captureBaseline()`) rather than per-field dirty flags, since the form has ~250 fields and the snapshot approach needed no per-field wiring. `resolveLeaveIntent()` gates every internal way of leaving the page with unsaved edits -- both "Back to Patients" links, and the date-selector change handler (which reverts the `<select>` back to the previous date on Cancel) -- via a custom 3-button modal (`showLeaveConfirmDialog`: Save and Leave / Discard and Leave / Cancel). "Save and Leave" is only offered when the visit is today's (`canSave`), matching the existing today-only save restriction; past-visit views only offer Discard/Cancel. A `beforeunload` listener covers the browser-level escape hatches (back button, tab close, URL bar) that JS can't intercept the same way -- it can only trigger the browser's own generic native confirmation, not this custom modal, which is an inherent platform limitation, not a gap in the implementation.
- **Blood/Pulse** (`/patients/{tz}/blood`): reuses `get_all_blood`/`add_blood_to_db` as-is; `delete_blood_from_db` is new (`Database/dbFuncs.py`) since the Qt app's "Delete a reading" button is a no-op (`def delete_blood(self): pass`). Reading time is always server-captured (`datetime.now().time()`), never user-entered, matching Qt. The date selector reuses the Visits tab's `/api/patients/{tz}/visits/dates` endpoint rather than duplicating it, since readings hang off the same `Visits` rows.
- **Diagnoses/Procedures** (`/diag-proc`, `app/diag_proc/routes.py`): the one module that isn't patient-specific — matches `DiagProcWindow`, which `MainWindow.show_diag_proc()` opens with no arguments and no "choose a patient first" guard, so the nav button on the patients page skips that guard too. Pick a diagnosis and/or procedure from two independently-filterable lists; the patients list is the **union** of both matches, not an intersection (`DiagProcWindow.update_patients_list()` adds both result sets into one `set()`). Reuses the existing `/api/diagnoses` and `/api/procedures` endpoints (already built for the Visits picker) for the two library lists rather than duplicating them; only the union-lookup endpoint (`/api/diag-proc/patients`) is new.
- **Static files revalidate on every load, on purpose.** `app/main.py` mounts static files through `RevalidateStaticFiles` (a `StaticFiles` subclass) rather than plain `StaticFiles`, adding `Cache-Control: no-cache` to every response. Starlette's `StaticFiles` sets no `Cache-Control` header at all by default, which lets browsers apply their own heuristic caching and can silently keep serving a stale JS/CSS file for a while after a change with zero revalidation — confirmed directly: a real edit to `patients.js` didn't show up in a browser until a hard refresh, and restarting the server (a red herring — server restarts don't touch client-side cache) didn't help. `no-cache` doesn't disable caching, it forces a conditional request (ETag) on every load, which `StaticFiles` already supports — so an unchanged file still comes back as a cheap `304`, only a changed one re-downloads.
- **Accounts:** manage with `python html_server/manage_users.py <username> --role admin|user` (prompts for password via `getpass`, no accounts ship pre-seeded).
- **Before any network-facing deployment:** set `CLINIC_WEB_SECRET_KEY` (session cookie signing key) via env var, and set `https_only=True` on the `SessionMiddleware` in `app/main.py` once served behind TLS — the session cookie is the entire auth mechanism.
